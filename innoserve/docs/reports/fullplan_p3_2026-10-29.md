## 2. job 容器與包裝腳本

**`arbiter/arbiter/sandbox.py`**（只用標準函式庫）。`JobSandbox` 每個 job 開一個容器：
- `docker run -d --rm --network none --read-only`；
- tmpfs：`/tmp`、`~/.foundry`、`~/.solc-select`（Slither 的 crytic-compile 一啟動就要在家目錄建這個資料夾，第一次試跑時因為唯讀根目錄而失敗，所以加了這個 tmpfs）；
- `--memory 2g --memory-swap 2g --cpus 2 --pids-limit 512 --cap-drop ALL --security-opt no-new-privileges --user <uid>:<gid>`；
- **只掛 job 目錄**，而且掛在相同路徑。
- 主程序是 `sleep <job_max>`（預設 1800 秒）。外面就算全部當掉，容器也會自己結束，並因 `--rm` 被移除。
- 同一時間只跑一個沙箱 job：用 `/tmp/arbiter-sandbox.lock` 的 flock，第二個 job 會等。
- 結束前讀 cgroup 的 `memory.peak`，然後 `docker rm -f`。

**`service/bin/forge|anvil|cast|slither` → `_sandbox_exec`**：
- 用 `docker exec` 轉進該 job 的容器，指令在 `env -i PATH=…` 和 `timeout -k 5 <上限>` 底下執行。上限：單次呼叫 600 秒，anvil 是 job 上限。
- 沒有設定 job 容器時**拒絕執行**（rc 126），絕不退回主機。
- forge 必須在 job 目錄裡被呼叫；anvil、cast、Slither 不管呼叫者在哪裡，都在 job 目錄裡執行。
- 轉送 SIGTERM／SIGINT。LiveChain 用 `terminate()` 停 anvil，實測 anvil 會乾淨結束。
- Slither 收到的 `--solc` 是主機上 `~/.svm/...` 的路徑，包裝腳本改寫成映像內的 `/opt/svm/...`（同樣的 sha256）。

**主機和容器的分工**：
- 主機：gate、agent 迴圈、Gateway（持有金鑰）、Python 程式。
- 容器：所有 forge／anvil／cast／Slither 呼叫。
- `TMPDIR` 指到 job 目錄，因為 prove 和 live_attack 會用 `tempfile`。

**anvil＋cast 走容器內 loopback**：
- `python3 -m arbiter.sandbox exec -- python3 scripts/live_attack.py` → PROVEN（5.6 秒）；`--patched` → NOT PROVEN。
- live_attack_stakingvault 原合約 PROVEN、`--patched spark-test-2` NOT PROVEN。

**Slither 也在沙箱裡**：映像內有同版 Slither，gate 在沙箱模式把 `ARBITER_SLITHER` 指到包裝腳本。結果和主機上跑的相同（spark-test-1、2 都是 reentrancy-eth，第 20 行）。

## 3. 開關與預設值

| 呼叫者 | 預設 | 理由 |
|---|---|---|
| **網頁上傳** | **一律開**，沒有關閉的開關 | 不受信任的程式碼。沙箱開不起來就判「無法判定（稽核未完成）」並寫原因與白話說明，不會改在主機上跑 |
| `python3 -m arbiter.gate` | `--sandbox on|off`，沒給就看 `ARBITER_SANDBOX`，都沒有就**關** | CLI 是我們自己在用；PR 整合（P5）時再決定是否預設開 |
| 網頁的預錄重播 | 跟 `ARBITER_SANDBOX`，預設**關** | 重播的攻擊在錄製時已經在這台機器上執行過，不是新的不受信任輸入；決賽主線靠預錄，少依賴 Docker Desktop 就少一個台上失敗點；開了只多約 2 秒，需要時 `ARBITER_SANDBOX=1` 啟動 web 即可 |
| demo_gate.sh、patch_probe、regression_probe、live_attack* | 預設**關**，可以用 `python3 -m arbiter.sandbox exec -- <指令>` 開 | 我們自己的程式。實測開沙箱也都照常：patch_probe 5/5（5.2 秒）、regression_probe 6/6（3.9 秒）、兩支真鏈 demo 正反兩向都對 |

- 沙箱要用卻不能用時：
  - `--file`：`not_executed`，reason `sandbox_unavailable: <原因>`，0 個 LLM 請求、0 次 forge；
  - `--from-results`：判定照錄製時的結果，但 A/B/G 標「無法重現（沙箱無法使用，沒有在主機上改跑）」，修補不重新驗證，Slither 不跑。
  - 實測：用不存在的映像名稱模擬，rc 2，0 個請求。
- 網頁 job 逾時（`FILE_TIMEOUT` 900 秒）：gate 程序被終止，網頁依 run-id 移除容器，顯示「無法判定（稽核未完成）」：「稽核超過 N 秒還沒完成，已被終止；這不代表合約沒有漏洞。」
- 結果頁加了一列「執行環境」：沙箱／未使用沙箱（重播）／沙箱無法使用。截圖：`reports/fullplan_p3/p3_sandboxed_upload.png`。

- 有一點照實記下：呼叫端被 SIGKILL 時，攔不到訊號，所以容器內那個指令會繼續跑，直到 job 結束容器被銷毀，或碰到單次 600 秒上限。它不會跑到 job 之外，但在同一個 job 裡會佔用 CPU 直到這兩者之一發生。
- 斷言 2 的假金鑰原本長得像 `sk-...`，被 repo 的 pre-commit 憑證掃描擋下。我改成 `PLACEHOLDER_*`，沒有用 `--no-verify`。

## 8. 留給後面段落的事

1. **相依快取的路徑對不上（P6 要處理）**：
   - `repo.py` 的 `DEFAULT_DEP_CACHE` 是主機的 `~/soldeps`，但本機根本沒有這個資料夾（從來沒建過）。映像裡的快取在 `/opt/soldeps`，而容器只掛 job 目錄。
   - 所以 repo 模式碰到 OpenZeppelin 這類 import 時，主機算出的 remapping 在容器裡找不到。
   - 單檔上傳（目前網頁唯一支援的輸入）不受影響。
   - P6 做 Foundry 專案時要決定：把需要的函式庫複製進 job 目錄，或讓 remapping 指向 `/opt/soldeps`。
2. chainlink 不在相依快取裡（build_dep_cache.sh 的 tag 錯誤）。
3. demo_gate.sh 啟動 web 時沒有設 `ARBITER_SANDBOX`，所以重播預設不進沙箱（照 §3 的決定）。上傳不受這個設定影響，一律在沙箱裡。
4. Docker Desktop 必須開著，網頁上傳才能用；沒開時上傳會被判「無法判定」，預錄重播照常。決賽前的檢查表要加這一項（P9）。
