## 0. P3、P5 留下的三件事

### 0.1 repo 模式的相依快取（做法：**把函式庫複製進 job 目錄**）

問題：
- remapping 寫的是絕對路徑，例如 `@openzeppelin/…=/home/…/soldeps/openzeppelin-v4/…`。
- 沙箱容器只掛 job 目錄（掛在同一個路徑），看不到 `~/soldeps`。
- 而且主機上根本沒有 `~/soldeps`，容器裡的那份在 `/opt/soldeps`。

做法：
- `repo.localize_dep_cache(dest)`：把快取的 `.sol` 檔（14 個套件、2,405 個檔、約 10 MB、約 2 秒）**複製**進 `<job>/soldeps`。
- 沙箱模式下，gate 把 `ARBITER_DEP_CACHE` 指向這份複製，`repo.py` 改讀 `default_dep_cache()`。
- job 結束、沒有 `--keep` 就刪掉。

選這個做法而不是「沙箱裡 remapping 指向 /opt/soldeps」的理由：
1. 容器「只掛 job 目錄」的規則不用破例，P3 的 sandbox_assertions 第 6 條（job 互相隔離）照樣成立。
2. 同一組 remapping 在主機和沙箱裡都對，不用改寫路徑。指向 /opt/soldeps 的話，主機也要有 /opt/soldeps（要 sudo），或在沙箱和主機之間改寫 remapping，而 remapping 是 workspace.py 寫入的（不能動）。
3. `repo.repair()` 在編譯器說找不到某個檔案時，會到其他套件找，所以複製整份，不只複製 `external_used` 列出的套件。
4. **用複製，不用硬連結**：job 目錄在容器裡可寫，透過硬連結寫入會改到之後每個 job 的快取。

主機的快取是從映像匯出的，`docker cp` 不需要連網，所以主機和容器解析的是同一批檔案。`service/sandbox/build.sh` 建完映像後會自動匯出到 `~/soldeps`（或 `$ARBITER_DEP_CACHE`）。

實測（`scripts/repo_patch_probe.py --sandbox` 的 sandbox_deps）：同一份 import OpenZeppelin `ReentrancyGuard` 和 chainlink `AggregatorV3Interface` 的合約，在容器裡：
- 不複製：編譯失敗（就是 P3 留下的缺口）。
- 複製：`prepare_context()` 成功，remapping 全部指向 job 目錄。

## 1. patch.py 的 repo 模式

- `exploit_from_row(row, project=…)`：
  - 在專案裡（PR 模式、`--project`），或合約有 import 時，回傳 `repo = {root, rel, solidity}`。`solidity` 是 harness 當初組的原樣，import `arbiter-target/<檔名>`。
  - 合約沒有 import 時，另外保留 hermetic 版，給 A/B/G 和回歸測試下載使用（行為和以前一樣）。
- `_Run(repo=…)`：每次建置都用 `copy_project()` 把專案複製到 `<work>/copies/<id>`，把（修補後的）原始碼寫進副本，對副本跑 `plan_for()` 和 `prepare_context()`。
  - ABI 從 `out/<檔名>/*.json` 讀（repo 模式的編譯產物不在 `out/Target.sol`）。
  - 複製時略過 `.git`、`node_modules`、`out`、`cache` 等 repo.py 不讀的資料夾，以及**所有符號連結**：上傳的專案裡，連結可能指向主機上任何地方，而副本就是容器看得到的範圍。
- `reproduce`、`verify_fix`、`repair` 都加了 `repo=`。不給時就是原本的 hermetic 流程，patch_probe 仍是 5/5。
- 有 import 的合約現在也能走修補閘門。repo_patch_probe 的 with_import：目標 import 專案裡的 `./IStakingVault.sol`，修補被接受。
- 回歸測試下載仍然只支援單一檔案；有 import 的合約，畫面寫「這份合約有 import；回歸測試下載目前只支援單一檔案的合約」。
- **使用者的原檔不會被改**：probe 對原專案前後做逐位元組雜湊比對，結果相同。

## 3. 檢查 5（修補後再攻擊，預設開）

- `patch.reattack()`：對修補後的合約呼叫 **`agent.audit(..., ruled_out=[用過的假設])`**，一次就是一個 attempt，回合數同稽核（`--max-turns`，預設 16）。agent.py 一行沒改，它本來就有 `ruled_out` 參數，會在使用者訊息加上「這些假設已經試過、不要再試」。
- 再攻擊的版面和原本的稽核相同：
  - 專案：複製後的專案。
  - 單一檔案：同名的一檔 repo。
  - 理由：10/28 實測，使用者訊息會決定模型選哪個謂詞（hermetic 5/5 選 eth_profit，repo 8/8 選 victim_loss）。再攻擊除了合約和排除的假設之外，不應該和第一次稽核有任何差別。
- `repair()` 改成回合式：
  1. 第 1 回合攻擊：原本的稽核。
  2. 防守：最多 3 個提案過檢查 0～4。
  3. 再攻擊：
     - 沒證實 → 接受修補，檢查 5 pass，用語固定為「**修補後再攻擊 1 次（N 回合）未成功**」，後面一定接「不代表合約安全，也不代表修好了所有漏洞」。
     - 沒跑完 → 檢查 5 skipped（不算通過）。
     - 證實新攻擊 → 這版修補拒收，新攻擊的假設加入 `ruled_out`。如果新攻擊是 victim_loss，就成為**檢查 1 的額外證據**：之後每個修補都必須讓原攻擊和這個新攻擊都失效。回饋訊息 `PATCH REJECTED: 5` 附上新攻擊的假設、漏洞函式、攻擊路徑，以及在修補版上量到的 A/B/G。
  4. 最多 2 次防守（攻 → 守 → 攻 → 守 → 攻）。第 3 次攻擊仍成功時停下，狀態 `rejected_reattack`，畫面寫「**修補未通過再攻擊**」，仍然擋部署。
- gate.json：
  - `patch.timeline`：每一格的回合、攻／守、結果、白話標籤、攻擊假設、漏洞函式、攻擊路徑、A/B/G、回合數、秒數、請求數、排除的假設、試過的假設；防守格有提案數、檢查結果、diff。
  - `patch.reattack`：enabled、status、label、requests、elapsed_s、attacks。
  - `patch.gate_checks["5"]`、`repo_tests`。
  - `repair_usage` 另外列出 `reattack_requests`、`reattack_s`（`llm_requests_repair` 包含再攻擊的請求）。
- PR 留言：「修補閘門：重現 通過、…、換手法再攻擊 通過」一行，加上回合表格（回合／誰／結果／細節）和再攻擊的結論句。
- 網頁結果頁：在修補標題下方加「攻防過程」時間軸，例如「第 1 回合：攻擊成功（已證實）→ 第 1 回合：修補通過檢查 → 第 2 回合：換手法攻擊：未成功（5 回合）」。
  - 攻擊格點開：攻擊假設（AI 原文）、漏洞函式、攻擊路徑、A/B/G 表、不准再用的假設、試過的假設、回合數／請求數／秒數。
  - 防守格點開：提案數、檢查燈號、這一版的 diff。
  - 修補閘門的燈號從 5 個變成 7 個（加上 4、5），新增狀態：不適用（單一檔案）、沒有跑（不算通過）、這次沒有開。
- 工作頁：活動紀錄多出「⚔️ 第 2 回合：修補通過檢查，AI 換一種手法再攻擊…」和結果兩行；燈號 4、5 即時更新。
  - 實測發現：最後一次重新驗證會清空燈號，造成檢查 5 顯示「沒有跑」。已修正，在最後一次驗證之後重送檢查 5。修正後 TwoDoorVault 的工作頁顯示正確（`screens/twodoor_job.png`）。

### 5.4 攻 → 守 → 攻 → 守 → 攻（不需要 LLM，`scripts/reattack_probe.py` 5/5）

模型的兩個角色用寫死的回應代替（修補提案是固定的 diff，再攻擊回固定結果），其他都是真的 repair 迴圈和修補閘門（forge）。兩扇門的 exploit 都是 harness 實際組出來的。

| 案例 | 結果 |
|---|---|
| doors | P_ALL（只修 withdrawAll）擋得住 E_ALL、擋不住 E_ONE（檢查 1 失敗）；P_BOTH 兩個都擋得住 |
| two_rounds | 攻成功 → 守 P_ALL → 攻成功（E_ONE）→ 守 P_BOTH → 攻未成功 → 接受；回饋訊息有 `PATCH REJECTED: 5`；第 2 次再攻擊排除 2 個假設；最終驗證時檢查 1 重跑 E_ONE 也失效 |
| extra_blocks | 被打穿後模型又交 P_ALL：檢查 1 擋下，訊息「the attack the re-audit found against your previous patch still succeeds」；再交 P_BOTH → 接受 |
| capped | 兩次再攻擊都成功 → 2 次防守後停下：`rejected_reattack`、檢查 5 fail，第 3 個修補沒有被要求 |
| not_run | 再攻擊沒跑完 → 修補靠 0～4 被接受，檢查 5 skipped（不算通過） |

## 7. 和計劃書不同之處（照現況）

- 計劃書 6.3 把檢查 5 寫成「選配」，這次照使用者決定**預設開啟**；`--reattack off` 可以關掉。
- 檢查 5 被打穿時，新攻擊不只是「回饋」，還成為**檢查 1 的額外證據**（之後的修補也必須讓它失效）。計劃書只寫「新 exploit 當成下一輪回饋」；不這樣做的話，模型可以把同一個被打穿的修補再交一次（reattack_probe 的 extra_blocks 就在測這個）。
- 檢查 4「修補前就跑不起來」記 skipped，修補仍然可以靠 0～3 被接受，但不顯示為通過。計劃書寫「不算通過」，沒有寫要不要因此拒收；我選「不拒收、照實標示」。
- 檢查 4 的 `forge test` 是在專案副本裡跑，用專案自己的 `foundry.toml` 和 `lib/`（加 `--offline`）。專案需要 git submodule 但 zip 裡沒附 `lib/` 的話會跑不起來，記 skipped。
- 再攻擊用「再開一個 attempt」實作（直接呼叫 `agent.audit`），沒有經過 `run_arbiter`，所以不會寫進 results.jsonl。結果寫在 gate.json 的 `patch.timeline` 和 `repair_usage`。
- 再攻擊不限制謂詞，模型可以用任何謂詞證實。新攻擊不是 victim_loss 時，仍然會拒收那版修補，但無法成為檢查 1 的額外證據，只靠下一次再攻擊把關。
- 回歸測試下載仍然只支援沒有 import 的單一檔案合約。
