## 2. dump 獨立重現（P1 §1 的已知問題）

- **原因**：dump 的 foundry.toml 一律 `via_ir = true`，但範本是 `optimizer = false`。
  harness 自己是預設 `via_ir = false`，遇到 Stack too deep 才開 IR，所以 dump 用的剛好是唯一會失敗的組合。
- **實測三種設定**（spark-test-2 的 dump）：`via_ir=false`＋`optimizer=false`、`via_ir=true`＋`optimizer=true`、`via_ir=false`＋`optimizer=true` 都 PASS。
  只有原本的 `via_ir=true`＋`optimizer=false` 會 Stack too deep。
- **選的修法**：先用 `via_ir=false`（和 harness 證實攻擊時的預設相同，最接近原本的執行環境）；只有輸出出現 Stack too deep 時，才改用 `via_ir=true`＋`optimizer=true` 再試一次。
  manifest 每筆多一個 `build` 欄位（`legacy` 或 `via_ir+optimizer`）。
  不用「via_ir＋optimizer 關」當 fallback，因為實測它正是會 stack too deep 的那個。
- **驗收**：
  - `cli.py dump --results runs/spark-test-2.results.jsonl` → `exploits_reproduced 1/1`（build＝legacy）。
  - 拿 dump 出來的 src 和測試檔跑 check 0：A/B/G 是 2/2/1、2/2/1、2/2/1、2/0/7，和原 run 相同。
  - spark-test-3、4、5 各 1/1。
  - V_reentrancy_unstake＋DRAIN（組成一筆結果列再 dump）：1/1，check 0 的 A/B/G 2/0/7 ×4。
- **prove 和 live_replay**：
  - `prove_dump` 只讀 manifest 的 `reproduces`，當作第二階 standalone 的旗標。`cli.py prove` 跑 spark-test-2 的 dump，現在 standalone 顯示 **yes**（之前是 no）。
  - live 欄仍是 `--`，和 10/28 報告相同：模型寫的攻擊上鏈不一致，不是這次造成的。
  - live_replay 用的是自己的 `build_project`（自帶 `via_ir = true`），和 dump 的設定無關，**沒有改**。真鏈 demo（live_attack、live_attack_stakingvault）照常。

## 3. Slither：slither_arm.py、static_hints.py

- **位置和指示不同**：可匯入的函式放在套件裡的新檔 `arbiter/arbiter/static_hints.py` 的 `run_slither()`，slither_arm.py 的 `run_one()` 改成呼叫它。
  原因是 gate.py 在 arbiter 套件裡，不應該 import `scripts/` 底下的模組；放在套件裡，gate 和對照臂就用同一份程式。
  它只用標準函式庫，Slither 用 subprocess 呼叫，arbiter 套件的相依沒有變。
- 暫存目錄由呼叫端傳入（原本開在家目錄底下）。每筆 finding 保留 `check`、`impact`、`confidence`、`line`、`end_line`、`function`（從 elements 的 source mapping 取）、`message`（Slither 的說明第一行，路徑是相對的）。
- 找 Slither 的順序：`$ARBITER_SLITHER`（有設定但路徑無效時視為「沒裝」，不往下找）→ PATH → repo 旁邊的 `venv-tools/bin/slither`（也就是 `~/innoserve/venv-tools`）。
- solc：從 forge 的 `~/.svm` 依 pragma 挑。結果列有 `context.solc` 時優先用它（spark-test 是 0.8.20），否則挑符合 pragma 的最新版（和 forge auto-detect 相同，v3 是 0.8.37）。
- **對照臂重跑**（0 個 LLM 請求）：`slither_arm.py` 跑 v3 的 40 份，結果和 AIS3 存下的 `runs/slither.json` **逐份、逐個 check 完全相同**：298 筆，Medium/Medium 是 TP 14、TN 10、FP 10、FN 6，MCC 0.204，0 份分析失敗。
  （AIS3 當時的 solc 沒有紀錄；這次是 0.8.37。）

## 5. proposals.py 的 Slither 轉換器（預設關閉）

照計劃書 Step 4 補三個缺口，Bastet 的既有路徑一行沒改：
1. **格式**：`slither_jobs()` 把 Slither 結果轉成 jobs.jsonl。每個 check 一列；參考語料裡有、這份沒觸發的 check 寫 `n_findings: 0`，所以 `load_hits` 和分母都看得到這份樣本。
   Informational、Optimization 排除（`solc-version` 在 40 份全部觸發）。
2. **前言**：`slither_proposal_block()` 用 Slither 自己的實測數字寫（v3 上 specificity 0.50），不再沿用描述 Bastet 的「true-negative rate is zero」。
   run.py 只加一個選用參數 `proposal_renderer`，預設仍是 `proposal_block`。
3. **罕見度**：`slither_rarity()` 用 `runs/slither.json` 的 40 份合約計算。例：reentrancy-eth 12%、reentrancy-benign 38%、tx-origin 2.5%。

- 接線：`gate --file … --slither-proposals` 才會打開。
- 驗證不呼叫 LLM：把 `run.audit` 換成假的函式，攔下 agent 收到的文字。
  - 加旗標時：收到 Slither 前言；
  - 不加旗標時：收到空字串；
  - run.py 用 Bastet jobs 時：文字和 `proposal_block` 逐字相同；
  - ledger 0 列。
- **維持關閉的原因**：計劃書 9.3 規定開不開由預註冊的 A/B 決定，這次沒跑（D4 把 A/B 留到賽後）。
  現有資料也不支持它會提高召回率：把 Bastet 命中餵給 agent 時，recall 從 0.450 降到 0.300；ARBITER 漏抓的 11 份裡只有 3 份有同類的 Slither check。
